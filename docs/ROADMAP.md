## Phase 2 — 배치 정책을 측정으로 결정한다 (1~1.5주) ✅ 측정 완료

**이 프로젝트의 본론.** 원래 계획은 "정책을 정하고 할당 래퍼로 구현"이었으나,
측정 결과 **래퍼가 옮길 것이 거의 없다**는 사실이 나왔다. 효과가 있는 레버는 전부
Kconfig 심볼이고, 그 심볼이 실제로 무엇을 얼마나 옮기는지는 문서에 없다.
그래서 이 Phase의 산출물은 래퍼가 아니라 **배치 정책 결정표**다.

> 방향 전환 기록 (2026-09-19). 래퍼는 버리지 않고 **Phase 4로 옮긴다.** LVGL 드로우
> 버퍼(DMA 필수 → 내부 SRAM)와 프레임버퍼(261,120 → PSRAM)는 물리적으로 강제되는
> 배치 결정이고, **거기엔 진짜 호출자가 있다.** 호출자 없는 API를 먼저 만들지 않는다.

### 전제 작업

- [x] **`CONFIG_PARTITION_TABLE_SINGLE_APP_LARGE`** (factory 1M → 1500K)
      heap tracing 을 켜기 전 앱 여유가 77,680 바이트(7%)뿐이었다. 먼저 올려두면
      빌드가 깨졌을 때 "코드가 안 들어가는 것"과 "측정이 안 되는 것"이 안 섞인다.
      OTA 미사용이라 비용 0, 바이너리 크기는 안 변하므로 A/B 비교표도 유효.
      **부수 효과: 앱 여유 7% → 36%. Phase 4의 LVGL 이 플래시 때문에 불가하다던
      제약이 풀렸다**
- [x] **heap tracing 도입** — `HEAP_TRACING_STANDALONE` + 해시맵(PSRAM).
      레코드 버퍼는 `EXT_RAM_BSS_ATTR` 로 PSRAM 에. 계측이 관측 대상인 내부 SRAM 을
      밀어내면 안 된다. 콜스택 깊이는 6 — 기본값 2 는 두 칸이 전부 할당기 껍데기
      (`heap_caps_malloc_default`, `malloc`)에 먹혀 호출자를 알 수 없다
      ⚠️ `SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY` 는 `EXT_RAM_BSS_ATTR` 만 옮기지
      않는다 — `liblwip.a` 의 `.bss` 전체(14,036)도 같이 나간다. 힙 풀이 그만큼
      커지므로 **이 빌드의 절대값은 A/B 기준선과 비교하면 안 된다**

### 관측 — 무엇이 내부 SRAM을 먹는가

- [x] TLS 피크 = **78,347 바이트** (실패 경로 80,723). `min_free` 로만 관측됨
- [x] 단편화는 **첫 요청에서 전부 발생하고 누적되지 않는다.** largest
      180,224 → 147,456 (-32,768) 이후 45회까지 평형
      → 정책은 "재배치" 가 아니라 **"부팅 시 큰 블록 선확보"** 로 간다
- [x] Wi-Fi 구동 비용 — A→C **48,312** / A→E **51,584**. 정적 영역을 14KB 늘려도
      한 바이트도 안 변한다. **정적 비용과 동적 비용은 독립**이고, 이것이 이후 모든
      차분 측정의 전제다 (빌드 3개에서 재확인)
- [x] 단편화율이 시간/요청 횟수에 비례해 누적되는가 — 아니다. **평형형**이다
- [x] **78KB 의 전수 분류** — heap tracing, 콜스택 6단, 270건.
      독립 실행 2회에서 합계 52,098 / 52,106 (8바이트 차)로 재현

      | lwIP `pbuf`/`mem` (`mem_clib_malloc`) | 9,272 | 85 | **17.8%** |
      | 하드웨어 AES DMA 바운스 | 4,256 | 63 | 8.2% |

### 정책 A/B — 각 스위치가 무엇을 얼마나 옮기는가

이 Phase 의 산출물. 스위치마다 **이동량 / 대가 / 판단**을 남긴다.

- [x] **`SPIRAM_TRY_ALLOCATE_WIFI_LWIP`** (유휴 기준) — 빌드 3개로 분해.
      켜면 내부 여유가 **오히려 17,868 줄어든다.** 배치 정책과 용량 정책이 한 심볼에
      묶여 있어(`esp_wifi/Kconfig:82` `depends on`) TX 버퍼가 dynamic→static 으로
      강제 전환되기 때문. 같은 TX 구성끼리 비교하면 이동량은 10,360(13%)뿐
- [x] **`MBEDTLS_EXTERNAL_MEM_ALLOC`** — 피크 78,347 → **47,039** (−31,308),
      largest 147,456 → **176,128** (+28,672), 단편화 손실 32,768 → 4,096 (1/8).
      PSRAM 이동 38,896. **유지하되 최종 답이 아니다 — 폴백이 없다**
      (`heap_caps_calloc(SPIRAM|8BIT)` 는 모자라면 그냥 `NULL`)
- [x] **`SPIRAM_TRY_ALLOCATE_WIFI_LWIP` 재평가 — 피크 기준.** 사정권을 콜스택
      분류로 먼저 **42,564** 로 예측하고 켰더니 내부 할당이 **42,716** 줄었다
      (152 바이트 차). 1,700 바이트 Wi-Fi RX 버퍼가 통째로 PSRAM 으로 넘어간다.
      **스위치는 이름대로 동작한다.**
      그러나 같은 조건식이 **여섯 군데**를 지배해 TX 버퍼가 dynamic 32 → static 16
      으로 강제 전환되고, 초기화가 상시 **+17,636**. 부하 중 largest 184,320 →
      **172,032** 로 목표 지표가 나빠진다. 탈출구로 보였던 `SPIRAM_IGNORE_NOTFOUND`
      는 PSRAM 선호 자체를 끈다(help 명시) + `ALLOW_BSS_SEG_EXTERNAL_MEMORY` 와
      상호배제라 선택 불가. → **기각 유지.** 상세: `STUDY.md §9`
- [x] **AES DMA 바운스의 인과 확인** — `MBEDTLS_INTERNAL` 로 한 줄 되돌려 확인.
      `esp_aes_process_dma_ext_ram` **19건 → 0건**, 1,600/1,179 바이트 덩어리가
      통째로 사라진다. 대가 **2,984** + 청크별 `memcpy` 확정
- [x] **정책 결정표 완성**

      | 스위치 | 이동량 | 대가 | 판단 |
      |---|---|---|---|
      | `MBEDTLS_EXTERNAL_MEM_ALLOC` | 38,896 → PSRAM | AES 바운스 2,984 + `memcpy`, 키가 외부 버스로 | **채택** |
      | `SPIRAM_TRY_ALLOCATE_WIFI_LWIP` | 42,716 → PSRAM | 초기화 +17,636, largest −12,288 | **기각** |
      | `PARTITION_TABLE_SINGLE_APP_LARGE` | — | 없음 | **채택** |

- [x] **계측 도구의 맹점 발견** — heap tracing 의 `--wrap` 은 같은 번역 단위 내부
      호출을 못 잡는다. `heap_caps_calloc_base()` → `heap_caps_malloc_base()` 가
      같은 파일이라 **mbedTLS 할당은 한 건도 기록되지 않는다.**
      분류 결과는 "추적된 내부 할당의 82%" 로 읽어야 한다. `TROUBLESHOOTING.md #4`

> ⚠️ **미측정으로 남은 것.** 덮지 말고 기록한다.
> ① PSRAM 이동의 **성능 대가** — 요청 시간 A/B 가 링크 품질 차이에 묻혀 분리 실패.
> 재려면 같은 AP·같은 시간대에 두 빌드를 연속으로 돌려야 한다. **메커니즘은
> 확정됐다** — AES DMA 바운스 버퍼를 거치며 청크마다 `memcpy` 가 붙는다. 남은 것은
> 그것이 몇 ms 인가뿐이다.
> ② **실패 핸드셰이크 경로의 피크** — EXTERNAL 빌드 55회가 전부 성공이라 A측
> 80,723 에 대응하는 값이 비었다. 최악값은 실패 경로에서 나온다.

**배우는 것:** `heap_caps` capability 체계, DMA 제약의 물리적 근거,

### 채택한 설정과 그 대가

`CONFIG_FREERTOS_USE_TRACE_FACILITY=y`. 워터마크 값만 보려면 필요 없다
(`uxTaskGetStackHighWaterMark`는 `INCLUDE_` 매크로가 항상 1,
`FreeRTOSConfig.h:219`). 이 심볼이 주는 것은 **핸들을 모르는 남의 태스크까지 한 번에
훑는 능력**이고, Phase 2 에서 내부 SRAM 을 먹는 것의 82% 가 Wi-Fi/lwIP 였으므로
정작 보고 싶은 것이 남의 태스크였다.

| 지점 | Phase 2 | Phase 3 | 차이 |
|---|---:|---:|---:|
| 힙 풀 1번 | 0x44190 | 0x434A8 | −3,304 |
| A 부팅 직후 | 319,599 | 313,751 | −5,848 |
| 부하 중 `min_free` | 224,808 | 218,980 | −5,828 |
| 부하 중 `largest` | 184,320 | 184,320 | **0** |

풀 축소 3,304 의 내역은 중간 빌드(트레이스 기능만 켜고 배열은 링커가 버린 상태,
풀 0x43B08)를 끼워 넣어 쪼갰다 — 트레이스 기능 1,160 + `s_status` 864(map 의
`.bss.s_status` 실측) + **미확정 1,280**. 마지막 1,280 은 DRAM 세그먼트 시작이
`3fc9c400` → `3fc9c700` 으로 밀린 것과 관계가 있어 보이나 확인하지 않았다.
중요한 것은 **`largest` 가 움직이지 않았다**는 점 — 이 계측의 대가는
"여유 5.8KB" 이지 "큰 블록 확보 능력" 이 아니다. Phase 2 에서 `TRY_ALLOCATE_WIFI_LWIP`
를 기각한 이유(largest −12,288)와 성격이 다르다.

| esp_timer | 3,584 | **3,100** | **14%** |
| wifi | 6,656 | 3,420 | 51% |
| http_load | 8,192 | **4,936** | 40% |
| **합계** | **34,560** | **18,444** | 47% |

Phase 2 에서 `largest` 4,096 을 얻으려고 AES 바운스 2,984 를 대가로 치렀는데,
스택에 18KB 가 놀고 있었다. 회수 대상은 대부분 힙에서 나온 스택
(`esp_timer`·`tiT`·`wifi`·`ipc`·`sys_evt`)이고, `mem_monitor`/`http_load` 둘만 `.bss` 다.

⚠️ 워터마크는 **관측된** 최악이지 가능한 최악이 아니다. 45회 요청 + 재연결 1회만
본 값이다. 실패 핸드셰이크 경로(미측정 항목)는 더 깊을 수 있다.

### 측정 결과 2 — 워터마크는 샘플링이 아니다

`#0` → `#6` 사이에 IDLE0 이 804 → 644, tiT 가 1,844 → 1,604 으로 **줄었다.** 두 출력
사이의 저점을 0xa5 패턴이 기억하고 있었다는 뜻이다. Phase 1 에서 힙 피크 78KB 중
38KB 를 놓친 것과 구조가 다르다 — **값은 안 놓치고, 시점만 못 잡는다.**

**✅ 예측력 검증됨.** 점 2개로 세운 식이라 예측력이 없을 수 있었는데, 아래 스택 축소

### 측정 결과 5 — 훅이 불리지 않았다

`http_load` 스택을 512 로 내려 일부러 넘겼다. 기대는 `vApplicationStackOverflowHook`
→ `esp_rom_printf` → `esp_system_abort` 였는데, 실제로 나온 것은 `_xt_context_save`
에서의 **Double exception** 이었다. **5회 전부 같은 결과.**

원인은 감지 시점이다. `CONFIG_FREERTOS_CHECK_STACKOVERFLOW_CANARY` 는 컨텍스트
스위치마다 스택 바닥 4워드를 보는 방식인데(`stack_macros.h:94`), 태스크가 첫
`ESP_LOGI` 체인 안에서 이미 스택을 넘겨 **스위치에 도달하지 못했다.** 스택 포인터가
할당 영역 밖으로 나간 상태에서 예외가 들어오면 예외 프레임을 저장할 곳이 없어
예외 처리 중 다시 예외가 난다 — 그것이 Double exception 이다.

**훅은 "넘치면 불리는 함수" 가 아니라 "넘긴 채로 살아남아 스위치까지 가면 불리는
함수" 다.** CPU 가 먼저 트랩하는 쪽이 이긴다. 훅이 유용한 경우는 조금 넘겨서
아직 굴러가는 상황이고, 크게 넘기면 훅 없이 죽는다.

> 다음에 할 것(선택): `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK=y` 로 바꿔 같은
> 실험을 반복한다. 워치포인트는 스택 끝 주소에 **쓰는 순간** 하드웨어가 트랩하므로
> 시점 의존이 없다. 대가는 디버그 워치포인트 1개 소비.

### 맹점

- **훅은 시점에 의존한다.** 위 「측정 결과 5」. CANARY 방식은 컨텍스트 스위치에서만
  검사하므로, 스위치 전에 죽는 오버플로우는 훅을 거치지 않는다.
- **ISR 스택은 안 잡힌다.** `port_IntStack[2][1536]`(`port.c:83`)은 평범한 `.bss`
  배열이라 0xa5 로 채워지지 않는다. 스캔 대상이 아니다. `.bss` 고정 비용이라 힙과는
  무관하지만, Wi-Fi 가 ISR 에서 많은 일을 하므로 실제 맹점이다.
- **`TaskStatus_t` 에 스택 총량이 없다.** `pxEndOfStack` 필드는 `portSTACK_GROWTH > 0`
  일 때만 컴파일되는데 Xtensa 는 음수다. "%" 는 설정값을 따로 알아야 구한다.
- **CANARY 는 4워드만 본다.** 컨텍스트 스위치마다 스택 바닥 4워드가 0xa5a5a5a5 인지
  검사할 뿐이라(`stack_macros.h:94`) 16바이트를 건너뛰어 망가뜨리면 놓친다.
  커널 주석도 "does not guarantee" 라고 적어 뒀다.

**배우는 것:** `uxTaskGetSystemState` / `vTaskGetInfo`, 스택 오버플로우 감지 메커니즘,
계측이 관측 대상에 개입하는 문제(Observer Effect)

**산출물:** 힙 + 스택이 함께 찍히는 시리얼 대시보드, 스택 여유 18,444 실측

> 여기서 Phase 2의 정책이 실제로 쓰인다. 프레임버퍼 255KB는 PSRAM에,
> DMA가 필요한 플러시 버퍼는 SRAM에 — **이 보드에서 물리적으로 강제되는 구조.**
> 플러시 버퍼 크기를 얼마로 할지가 이 프로젝트에서 가장 설계다운 결정 중 하나다.

> ✅ **~~IRAM이 100%라 링크 에러로 튄다~~ — 확인해 보니 아니다 (2026-09-19).**
> `idf.py size` 의 `IRAM 16,384 / 16,384 (100.0%)` 는 **툴의 표시 구분이지 링커의
> 제약이 아니다.** 맵을 열면 링커가 보는 영역은 하나뿐이다 —
> `iram0_0_seg org=0x40374000 len=0x57700`(358,144). 실제 사용은
> `.iram0.vectors`(0x404) + `.iram0.text`(0x1820b) = **0x18700(100,096)**,
> 즉 **258,048 바이트가 남아 있다.** 링커의 판정식도 그대로 맵에 있다 —
> `ASSERT((_iram_end - ORIGIN(iram0_0_seg)) <= LENGTH(iram0_0_seg))`.
>
> `idf.py size` 가 100% 라고 한 16KB 는 SRAM0 의 0x40374000~0x40378000 구간이고,
> 이미 넘쳐서 **83,712 바이트가 DIRAM 쪽으로 흘러 들어가 있다**(`DIRAM .text 83,471`).
> 넘친 만큼은 데이터 쪽 주소에서 `.dram0.dummy` 로 예약된다:
>
> ```
> .dram0.dummy  0x3fc88000  0x14700   ; = _iram_end(0x4038c700) - _diram_i_start(0x40378000)
> .dram0.data   0x3fc9c700            ; 그만큼 밀려난다
> ```
>
> **그래서 진짜 대가는 링크 에러가 아니라 힙이다.** `IRAM_ATTR` 코드가 N 바이트 늘면
> `.dram0.dummy` 가 N 늘고, `.dram0.data`/`.bss` 와 `_heap_start`(현재 `0x3fca5668`)
> 가 통째로 N 밀려 **힙 풀이 1:1 로 줄어든다.** 조용히 줄어들기 때문에 링크 에러보다
> 나쁘다. LCD/LVGL 을 얹을 때 봐야 할 숫자는 `IRAM %` 가 아니라 맵의
> **`.dram0.dummy` 크기**다.
>
> 💡 이것이 Phase 3 에서 **미확정으로 남긴 1,280** 의 메커니즘이기도 하다.
> `USE_TRACE_FACILITY` 를 켜자 `_data_start` 가 `3fc9c400` → `3fc9c700` 으로 밀린 것은
> 트레이스 코드가 IRAM 을 늘려 `.dram0.dummy` 가 커진 결과다. 심볼을 끄고 한 번 더
> 빌드해 `.dram0.dummy` 를 비교하면 확정된다 (보드 없이 맵 파일만으로 가능).

> 💡 플러시 버퍼가 쓸 수 있는 내부 연속 블록은 부하 중 **176,128 바이트**다
> (mbedTLS EXTERNAL 적용 후. 적용 전에는 147,456이었다). 프레임버퍼 261,120 기준
> 부족분 **84,992** — 이 숫자가 "프레임버퍼는 PSRAM" 이라는 전제의 근거다.
> 상세: `STUDY.md §9` mbedTLS 할당자 A/B

### 배치 래퍼 — 여기서 태어난다

Phase 2 에서 내려온 것. **호출자가 둘 생기는 시점이 지금**이므로 여기서 만든다.
프레임버퍼는 PSRAM, DMA 플러시 버퍼는 내부 SRAM — 취향이 아니라 물리적 강제다.

- [ ] 크기 + DMA 필요 여부로 리전을 정하는 함수 하나 (구조체는 필요해지면 그때)
- [ ] **DMA 필수 요청은 PSRAM 으로 폴백하지 않기.** 할당은 성공해도 쓸 수 없으니
      실패만 못하다. 반대로 DMA 가 필요 없는 요청은 PSRAM 폴백을 허용한다
- [ ] 검증: `esp_ptr_internal()` / `esp_ptr_external_ram()` 으로 의도대로 갔는지 로그
- [ ] 플러시 버퍼 크기 결정 — 내부 연속 블록 176,128 안에서 몇 줄치를 잡을 것인가.
      **이 프로젝트에서 가장 설계다운 결정**

> 래퍼를 Phase 2 가 아니라 여기 둔 이유: mbedTLS `CUSTOM` 훅은 시그니처가
> `(size_t n, size_t size)` 뿐이라 의도도 DMA 플래그도 수명도 못 받는다. 반면
> LVGL 쪽은 **호출자가 의도를 알고 있다.** 래퍼에 의도를 넘길 수 있는 첫 호출자가
> 여기서 생긴다.

**배우는 것:** `esp_lcd` 패널 드라이버, QSPI 인터페이스, LVGL 구조,
DMA 플러시 버퍼가 왜 내부 SRAM이어야 하는지, 설계를 호출자 쪽에서 끌어내는 순서

**산출물:** 동작하는 대시보드, 데모 영상, 의도 → 리전 매핑이 로그로 증명됨

## 나중에 여유가 생기면

당장은 범위 밖. 더 파고들고 싶을 때의 확장 방향.

- ~~**정책을 교체 가능하게** 만들어 고정 임계값 방식과 단편화율 기반 적응형 방식을
  같은 부하에서 비교~~ → **임계값으로 가를 할당 자체가 거의 없다.** 내부 소비의
  82%가 Wi-Fi/lwIP 이고 그건 Kconfig 심볼로 통째로 움직인다. 적응형 정책은 옮길
  대상이 있을 때 의미가 있다
- ~~**mbedTLS 할당자 후킹**~~ → Phase 2 본론으로 올렸다가, 실측 후 **다시 내렸다.**
  mbedTLS 가 직접 잡는 몫은 `EXTERNAL` 한 줄로 이미 다 PSRAM 으로 갔고, 훅으로
  추가로 옮길 것은 `esp_tls_init` 1,764 바이트 수준이다. 남은 명분은 "폴백" 뿐인데
  그것만으로 정책 엔진을 만들 이유는 없다
- **계측 오버헤드 정량화** — 대시보드 on/off로 같은 부하를 돌려 비교
- **메모리 출처별 분리 계상** — 앱 / 서드파티 / 계측 자신
