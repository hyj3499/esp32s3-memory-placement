# 개발 로드맵

전체 약 6~7주. 공부와 데모를 목적으로 하며, 범위를 의도적으로 좁게 잡는다.

## Phase 0 — 환경 구축 (거의 완료)

- [x] ESP-IDF 설치 — v5.5.5, `C:\Espressif\frameworks\esp-idf-v5.5.5`
- [x] `hello_world` 빌드 → 플래시 → 시리얼 출력 확인 (COM9)
- [x] 프로젝트 골격 생성, `idf.py set-target esp32s3` 빌드 통과
- [x] 플래시 4MB 설정 (기본값 2MB라 절반을 못 쓰고 있었음)
- [x] PSRAM 인식 — **8MB Octal 확정** (Quad로 두면 무한 재부팅.
      `docs/TROUBLESHOOTING.md #1`)
- [x] `StackType_t` = `uint8_t` 확인 → **스택 단위는 워드가 아니라 바이트**
      (`portmacro.h:88`)
- [x] `multi_heap_info_t` 필드 확인 (`multi_heap.h:163`)
- [ ] **LCD 점등 확인** — 사각형 하나라도 그려지면 성공. 반나절.

> ⚠️ **NV3041A는 IDF 내장 드라이버가 아니다.** IDF가 제공하는 패널 드라이버는
> `nt35510` / `ssd1306` / `st7789` 3종뿐. 컴포넌트 레지스트리에서 받거나 초기화
> 시퀀스를 직접 써야 한다. QSPI 인터페이스라 SPI 설정도 까다로운 편.
>
> 여기서 하는 건 **구현이 아니라 리스크 정찰**이다. 못 띄우는 경우 대안(시리얼 +
> PC 그래프)을 일찍 준비해야 하므로 지금 확인만 해둔다. 대시보드는 Phase 4.

**산출물:** 빌드되는 프로젝트, PSRAM 8MB 인식 로그, LCD 점등 여부 판정

## Phase 1 — 최소 계측 + Wi-Fi/TLS 부하 (1주)

**프로젝트의 심장이 뛰기 시작하는 단계.** 힙 숫자가 부하에 반응해 움직이는 걸
시리얼로 본다.

### 최소 계측 (반나절)

거창할 필요 없다. 래퍼도 정책도 LVGL도 필요 없다. 숫자만 찍히면 된다.

- [ ] `heap_caps_get_info()`로 SRAM / PSRAM 각각 스냅샷
- [ ] `free` / `largest_free_block` / `minimum_free_bytes` 를 주기적으로 시리얼 출력
- [ ] 단편화율 계산 — `1 - largest_free_block / total_free_bytes`

### Wi-Fi + TLS 부하

- [ ] Wi-Fi 연결
- [ ] HTTPS 반복 요청 (`esp_http_client`)
- [ ] 이미지 수신 (선택 — 큰 버퍼 할당이 목적)

> ⚠️ **Wi-Fi 비밀번호를 커밋하지 말 것.** 공개 레포라 git 히스토리에 남으면 지우기
> 번거롭다. `menuconfig`로 빼거나 별도 헤더를 `.gitignore`에 넣는다.
>
> 💡 인증서는 `esp_crt_bundle`을 쓴다 (`CONFIG_MBEDTLS_CERTIFICATE_BUNDLE`).
> 공용 루트 CA 번들이라 개별 인증서 없이 공개 HTTPS 사이트에 붙는다.
>
> ⚠️ 플래시 4MB라 Wi-Fi + mbedTLS까지는 괜찮지만 나중에 LVGL을 얹으면 기본 파티션
> 테이블로 부족할 수 있다. 안 들어갈 때 손보면 된다.

**배우는 것:** `heap_caps_get_info` 지표의 의미, `minimum_free_bytes`가 왜 중요한지,
Wi-Fi 스택이 SRAM을 얼마나 가져가는지, TLS 핸드셰이크의 메모리 사용 패턴

**산출물:** 부하에 따라 움직이는 힙 로그

## Phase 2 — 관측·분석 → 정책 설계 + 할당 래퍼 (1~1.5주)

Phase 1의 데이터를 근거로 정책을 정하고, 그걸 코드로 만든다.

### 분석 먼저

- [ ] TLS가 어떤 크기를 얼마나 할당/해제하는가
- [ ] Wi-Fi 구동 시 SRAM 가용량이 얼마로 떨어지는가
- [ ] 단편화율이 어디까지 오르는가 / 시간에 따라 누적되는가
- [ ] **이 데이터로 임계값 결정** ← 감이 아니라 근거

### 래퍼 구현

- [ ] 요청 구조체 — 크기 / DMA 필요 여부 / 수명
- [ ] 리전 결정 함수 (고정 규칙 하나면 충분)
- [ ] 리전 → caps 변환, `heap_caps_malloc()` 호출
- [ ] **DMA 필수 요청은 PSRAM으로 폴백하지 않기**
      (할당은 성공해도 쓸 수 없으니 실패만 못하다)
- [ ] 검증: `esp_ptr_internal()` / `esp_ptr_external_ram()`으로 의도대로 갔는지 확인

**배우는 것:** `heap_caps` capability 체계, DMA 제약의 물리적 근거,
측정 데이터로 설계 결정을 내리는 과정

**산출물:** 의도 → 리전 매핑이 로그로 증명됨 + 임계값의 근거 데이터

## Phase 3 — 모니터링 확장 (3~4일)

힙 말고 스택도 본다.

- [ ] 태스크 스택 워터마크 — `uxTaskGetSystemState()`, **반드시 정적 버퍼로**
      (여기서 동적 할당을 쓰면 계측이 관측 대상을 오염시킨다)
- [ ] 스택 오버플로우 훅 등록 — `vApplicationStackOverflowHook`
- [ ] 모니터 태스크로 정리 (수집 주기 일원화)

**배우는 것:** `uxTaskGetSystemState` / `vTaskGetInfo`, 스택 오버플로우 감지 메커니즘,
계측이 관측 대상에 개입하는 문제(Observer Effect)

**산출물:** 힙 + 스택이 함께 찍히는 시리얼 대시보드

## Phase 4 — LCD 대시보드 (1.5~2주)

프로젝트의 얼굴. 데이터가 이미 검증돼 있으므로 **표현만 얹는 단계.**

- [ ] NV3041A 패널 드라이버 (Phase 0에서 확인한 방법으로)
- [ ] LVGL 통합 (`idf.py add-dependency`)
- [ ] **드로우 버퍼를 부팅 시 1회 할당** (런타임 단편화에 기여하지 않도록)
- [ ] 리전별 단편화 바
- [ ] 태스크 스택 워터마크 테이블
- [ ] 힙 사용량 시계열 그래프 (링버퍼)
- [ ] 프레임버퍼 덤프 유틸 — 포폴 이미지용 (LCD 직촬은 모아레로 품질이 나쁨)

> 여기서 Phase 2의 정책이 실제로 쓰인다. 프레임버퍼 255KB는 PSRAM에,
> DMA가 필요한 플러시 버퍼는 SRAM에 — **이 보드에서 물리적으로 강제되는 구조.**
> 플러시 버퍼 크기를 얼마로 할지가 이 프로젝트에서 가장 설계다운 결정 중 하나다.

**배우는 것:** `esp_lcd` 패널 드라이버, QSPI 인터페이스, LVGL 구조,
DMA 플러시 버퍼가 왜 내부 SRAM이어야 하는지

**산출물:** 동작하는 대시보드, 데모 영상

## 나중에 여유가 생기면

당장은 범위 밖. 더 파고들고 싶을 때의 확장 방향.

- **정책을 교체 가능하게** 만들어 고정 임계값 방식과 단편화율 기반 적응형 방식을
  같은 부하에서 비교
- **mbedTLS 할당자 후킹** (`mbedtls_platform_set_calloc_free`) — 단편화의 주원인을
  정책 통제 범위로 편입
- **계측 오버헤드 정량화** — 대시보드 on/off로 같은 부하를 돌려 비교
- **메모리 출처별 분리 계상** — 앱 / 서드파티 / 계측 자신
