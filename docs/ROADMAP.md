## Phase 1 — 최소 계측 + Wi-Fi/TLS 부하 (1주)

**프로젝트의 심장이 뛰기 시작하는 단계.** 힙 숫자가 부하에 반응해 움직이는 걸
시리얼로 본다.

### 최소 계측 (반나절)

거창할 필요 없다. 래퍼도 정책도 LVGL도 필요 없다. 숫자만 찍히면 된다.

- [x] `heap_caps_get_info()`로 SRAM / PSRAM 각각 스냅샷 (`mem_snapshot.c`, caps 4종)
- [x] `free` / `largest_free_block` / `minimum_free_bytes` 를 시리얼 출력
- [x] 위 출력을 **주기적으로** — `mem_monitor.c`, 5초 주기 한 줄 요약.
      정적 스택/TCB 로 올려 계측이 힙을 건드리지 않게 했다(대가 14,288 바이트).
      **한계 확인:** 5초 샘플링은 TLS 피크 78KB 중 38KB 를 놓쳤다. 피크는
      `min_free` 로만 잡힌다. 수집 주기 일원화는 Phase 3
- [x] 단편화율 계산 — `1 - largest_free_block / total_free_bytes`
      ⚠️ 이 공식은 두 가지 이유로 값을 부풀린다(여러 힙 합산, TLSF 크기 클래스
      내림). 절대값이 아니라 baseline 대비 증가분으로만 읽는다. `STUDY.md §7`

### Wi-Fi + TLS 부하

- [x] Wi-Fi 연결 — 단계별 계측 B~E 포함 (`wifi_conn.c`)
      절전은 `WIFI_PS_NONE`으로 껐다. 약한 링크에서 reason 4로 끊긴다
- [x] HTTPS 반복 요청 (`esp_http_client`) — `http_load.c`, start/stop API.
      매 요청 새 연결(`keep_alive_enable = false`)로 핸드셰이크를 반복시킨다.
      45회 무누수 확인. 상세: `STUDY.md §9`
- [ ] 이미지 수신 (선택 — 큰 버퍼 할당이 목적)

> ⚠️ **Wi-Fi 비밀번호를 커밋하지 말 것.** 공개 레포라 git 히스토리에 남으면 지우기
> 번거롭다. `menuconfig`로 빼거나 별도 헤더를 `.gitignore`에 넣는다.
>
> 💡 인증서는 `esp_crt_bundle`을 쓴다 (`CONFIG_MBEDTLS_CERTIFICATE_BUNDLE`).
> 공용 루트 CA 번들이라 개별 인증서 없이 공개 HTTPS 사이트에 붙는다.
>
> ⚠️ 플래시 4MB라 Wi-Fi + mbedTLS까지는 괜찮지만 나중에 LVGL을 얹으면 기본 파티션
> 테이블로 부족할 수 있다. 안 들어갈 때 손보면 된다.

**배우는 것:** `heap_caps_get_info` 지표의 의미, `minimum_free_bytes`가 왜 중요한지,
Wi-Fi 스택이 SRAM을 얼마나 가져가는지, TLS 핸드셰이크의 메모리 사용 패턴

**산출물:** 부하에 따라 움직이는 힙 로그

## Phase 2 — 관측·분석 → 정책 설계 + 할당 래퍼 (1~1.5주)

Phase 1의 데이터를 근거로 정책을 정하고, 그걸 코드로 만든다.

### 전제 작업

- [ ] **`CONFIG_PARTITION_TABLE_SINGLE_APP_LARGE`** (factory 1M → 1500K)
      앱 여유가 77,680 바이트(7%)뿐이라 heap tracing 코드가 들어갈지 아슬아슬하다.
      먼저 올려두면 "측정이 안 되는 건지 안 들어가는 건지"가 안 섞인다. OTA를
      안 쓰므로 비용 0이고, 바이너리 크기 자체는 안 변하므로 A/B 비교표도 안 깨진다

### 분석 먼저

- [x] TLS 피크 = **78,347 바이트** (실패 경로 80,723). `min_free` 로만 관측됨
- [x] 단편화는 **첫 요청에서 전부 발생하고 누적되지 않는다.** largest
      180,224 → 147,456 (-32,768) 이후 45회까지 평형
      → 정책은 "재배치" 가 아니라 **"부팅 시 큰 블록 선확보"** 로 간다
- [x] Wi-Fi 구동 시 SRAM 가용량이 얼마로 떨어지는가 — A→C **48,312** /
      A→E **51,584**. 정적 영역을 14KB 늘려도 한 바이트도 안 변했다.
      **정적 비용과 동적 비용은 독립**이고, 이것이 이후 모든 차분 측정의 전제다
- [x] 단편화율이 어디까지 오르는가 / 시간에 따라 누적되는가 — 위 항목에서 답이
      나왔다(중복). **평형형**이다
- [x] **mbedTLS 할당자 정책 전환 측정** ← 최우선 레버였다. **완료 (2026-09-19).**
      `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` 한 줄.
      **TLS 피크 78,347 → 47,039 (−31,308)**,
      **largest 147,456 → 176,128 (+28,672)**, PSRAM 이동 38,896,
      단편화 손실 32,768 → 4,096 (1/8). 상세: `STUDY.md §9`
      → **EXTERNAL 유지.** 단 최종 답이 아니라 **중간 기착지**다 — 폴백이 없다
- [ ] **내부에 남은 47,039 바이트의 정체** ← heap tracing 의 표적.
      "TLS 전체" 가 아니다. `mbedtls_calloc` 을 안 거치는 경로
      (esp-tls / esp_http_client / lwIP)와 `SPIRAM_MALLOC_ALWAYSINTERNAL=16384`
      에 걸린 16KB 이하 malloc 이 후보. `CONFIG_HEAP_TRACING_STANDALONE` +
      `heap_trace_dump_caps`. 차분법으로는 총량까지가 한계다
      ⚠️ 레코드 버퍼는 `heap_trace_record_t` 약 40바이트 × N. 내부 SRAM에 정적으로
      잡으면 계측이 관측 대상을 밀어낸다. `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY`
      + `EXT_RAM_BSS_ATTR` 로 PSRAM에 두고, 첫 핸드셰이크 구간만 트레이싱한다
- [ ] **이 데이터로 임계값 결정** ← 감이 아니라 근거
- [x] **`CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP` A/B 측정** — 빌드 3개로 분해 완료.
      결과: 켜면 내부 여유가 **오히려 17,868 줄어든다.** 배치 정책과 용량 정책이
      한 Kconfig 심볼에 묶여 있어(`esp_wifi/Kconfig:82` `depends on`) TX 버퍼가
      dynamic→static으로 강제 전환되기 때문. 같은 TX 구성끼리 비교하면 PSRAM으로
      옮겨지는 양은 10,360(13%)뿐. **IDF 기본값을 유지한다.** 상세: `STUDY.md §9`

> ⚠️ **미측정으로 남은 것 두 개.** 덮지 말고 기록해 둔다.
> ① PSRAM 이동의 **성능 대가** — 요청 시간 A/B가 링크 품질 차이에 묻혀 분리 실패했다.
> 재려면 같은 AP·같은 시간대에 두 빌드를 연속으로 돌려야 한다.
> ② **실패 핸드셰이크 경로의 피크** — B측 55회가 전부 성공이라 A측 80,723에 대응하는
> 값이 비었다. 최악값은 정상 경로가 아니라 실패 경로에서 나온다.

### 래퍼 구현

**명분이 바뀌었다.** `EXTERNAL` 한 줄로 31KB가 빠졌으므로 래퍼가 "총량을 옮기는
물건"일 이유는 사라졌다. 남은 명분은 **폴백**과 **선택적 이동** 둘이다.

첫 호출자를 `mbedtls_platform_set_calloc_free()` 로 확정하고 거기서 역으로 API를
뽑는다. 범용 API를 먼저 설계하면 부르는 데가 없어 데모에서 죽은 코드가 된다.

- [ ] `CONFIG_MBEDTLS_CUSTOM_MEM_ALLOC` + `mbedtls_platform_set_calloc_free()` 후킹
- [ ] **크기만으로 판단하는 최소 래퍼.** 훅 시그니처가 `(size_t n, size_t size)`
      뿐이라 의도도 DMA 플래그도 수명도 안 넘어온다. **줄 수 있는 정보가 크기밖에
      없다는 제약이 곧 설계 제약이다**
- [ ] 임계값 이상 → PSRAM, 미만 → 내부 SRAM. 임계값은 위 크기 분포에서 나온다
- [ ] **PSRAM 실패 시 내부로 폴백** — `esp_mem.c` 의 EXTERNAL 경로에 없는 것이 바로
      이것이다(`heap_caps_calloc(SPIRAM|8BIT)` 는 모자라면 그냥 `NULL`).
      래퍼의 존재 이유 절반이 여기 있다
- [ ] 검증: `esp_ptr_internal()` / `esp_ptr_external_ram()` 으로 의도대로 갔는지 확인
- [ ] 같은 부하를 다시 돌려 EXTERNAL(전부 이동) 대비 largest / 요청 시간 비교

> 의도·수명 같은 필드를 요청 구조체에 넣는 것은 **Phase 4로 미룬다.** LVGL 드로우
> 버퍼가 두 번째 호출자로 붙을 때 "DMA 필수라 PSRAM 폴백 금지" 라는 실제 요구가
> 생긴다. 그때 확장해야 확장에 근거가 생긴다.

**배우는 것:** `heap_caps` capability 체계, DMA 제약의 물리적 근거, 측정 데이터로
설계 결정을 내리는 과정, **컴포넌트가 자기 할당자 정책을 따로 갖는다는 것**

**산출물:** 의도 → 리전 매핑이 로그로 증명됨 + 임계값의 근거 데이터

## Phase 4 — LCD 대시보드 (1.5~2주)

프로젝트의 얼굴. 데이터가 이미 검증돼 있으므로 **표현만 얹는 단계.**

- [ ] NV3041A 패널 드라이버 (Phase 0에서 확인한 방법으로)
- [ ] LVGL 통합 (`idf.py add-dependency`)
- [ ] **드로우 버퍼를 부팅 시 1회 할당** (런타임 단편화에 기여하지 않도록)
- [ ] 리전별 단편화 바
- [ ] 태스크 스택 워터마크 테이블
- [ ] 힙 사용량 시계열 그래프 (링버퍼)
- [ ] 프레임버퍼 덤프 유틸 — 포폴 이미지용 (LCD 직촬은 모아레로 품질이 나쁨)

> 여기서 Phase 2의 정책이 실제로 쓰인다. 프레임버퍼 255KB는 PSRAM에,
> DMA가 필요한 플러시 버퍼는 SRAM에 — **이 보드에서 물리적으로 강제되는 구조.**
> 플러시 버퍼 크기를 얼마로 할지가 이 프로젝트에서 가장 설계다운 결정 중 하나다.

> ⚠️ **IRAM이 이미 100%다** (16,384 / 16,384. `.text` 15,356 + `.vectors` 1,028).
> `IRAM_ATTR`가 붙은 코드가 조금이라도 늘면 **링크 에러로 튄다.** LCD/LVGL을 얹을 때
> 가장 먼저 터질 자리이므로 `idf.py size`를 먼저 보고 시작한다.

> 💡 플러시 버퍼가 쓸 수 있는 내부 연속 블록은 부하 중 **176,128 바이트**다
> (mbedTLS EXTERNAL 적용 후. 적용 전에는 147,456이었다). 프레임버퍼 261,120 기준
> 부족분 **84,992** — 이 숫자가 "프레임버퍼는 PSRAM" 이라는 전제의 근거다.
> 상세: `STUDY.md §9` mbedTLS 할당자 A/B

**배우는 것:** `esp_lcd` 패널 드라이버, QSPI 인터페이스, LVGL 구조,
DMA 플러시 버퍼가 왜 내부 SRAM이어야 하는지

**산출물:** 동작하는 대시보드, 데모 영상

## 기록 습관

겪은 문제는 **그때그때** 적어둔다. 나중에 몰아서 쓰려면 기억나지 않고, 포폴
트러블슈팅 항목은 실제로 겪은 것만 쓸 수 있다.
