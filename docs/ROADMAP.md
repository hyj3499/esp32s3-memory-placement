# 개발 로드맵

전체 약 6~7주. 공부와 데모를 목적으로 하며, 범위를 의도적으로 좁게 잡는다.

**원칙 하나:** 시리얼로 숫자를 먼저 맞추고 LCD를 얹는다. 순서를 뒤집으면 값이
틀렸을 때 데이터가 문제인지 UI가 문제인지 구분할 수 없다.

---

## Phase 0 — 환경 구축 (1주)

여기서 막히면 뒤가 전부 막히므로 먼저 확인만 하고 넘어간다.

- [ ] ESP-IDF 설치 (Windows 오프라인 인스톨러, `C:\Espressif`)
- [ ] `hello_world` 빌드 → 플래시 → 시리얼 출력 확인
- [ ] 프로젝트 골격 생성, `idf.py set-target esp32s3` 빌드 통과
- [ ] PSRAM 인식 확인 — `heap_caps_get_free_size(MALLOC_CAP_SPIRAM)`이 0이 아닌지
      (0이면 menuconfig의 Quad/Octal 설정이 보드와 안 맞는 것)
- [ ] LCD **점등만** 확인 (사각형 하나라도 그려지면 성공)

**배우는 것:** ESP-IDF 빌드 시스템, Kconfig, 컴포넌트 구조, PSRAM 활성화 과정

**산출물:** 빌드되는 빈 프로젝트, PSRAM 인식 로그

---

## Phase 1 — 할당 래퍼 (1주)

의도를 넣으면 올바른 리전에 할당되는 얇은 레이어를 만든다.

- [ ] 요청 구조체 정의 — 크기 / DMA 필요 여부 / 수명
- [ ] 리전 결정 함수 (고정 규칙 하나면 충분)
- [ ] 리전 → caps 변환, `heap_caps_malloc()` 호출
- [ ] **DMA 필수 요청은 PSRAM으로 폴백하지 않기** (할당돼도 못 쓰므로 실패만 못함)
- [ ] 검증: `esp_ptr_internal()` / `esp_ptr_external_ram()`으로 의도대로 갔는지 로그 확인

**배우는 것:** `heap_caps` capability 플래그 체계, SRAM/PSRAM의 실제 차이, DMA 제약

**산출물:** 의도 → 리전 매핑이 로그로 증명됨

---

## Phase 2 — 모니터링 (1주)

LCD에 그리기 전에 **숫자를 먼저 맞춘다.**

- [ ] 힙 스냅샷 — `heap_caps_get_info()`로 리전별 free / largest free block
- [ ] 단편화율 계산 — `1 - largest_free_block / free_bytes`
- [ ] 태스크 스택 워터마크 — `uxTaskGetSystemState()`, **정적 버퍼로**
      (여기서 동적 할당을 쓰면 계측이 관측 대상을 오염시킨다)
- [ ] 스택 오버플로우 훅 등록 — `vApplicationStackOverflowHook`
- [ ] 모니터 태스크에서 주기적으로 시리얼 출력

**배우는 것:** 단편화의 정량적 정의, `uxTaskGetSystemState` / `vTaskGetInfo`,
스택 오버플로우 감지 메커니즘, 계측이 관측 대상에 개입하는 문제

**산출물:** 시리얼에 찍히는 힙·스택 상태

---

## Phase 3 — LCD 대시보드 (1.5~2주)

프로젝트의 얼굴. 가장 오래 걸릴 가능성이 높다.

- [ ] LVGL 통합 (`idf.py add-dependency`로 컴포넌트 매니저 사용)
- [ ] **드로우 버퍼를 부팅 시 1회 할당** (런타임 단편화에 기여하지 않도록)
- [ ] 리전별 단편화 바
- [ ] 태스크 스택 워터마크 테이블
- [ ] 힙 사용량 시계열 그래프 (링버퍼)

**배우는 것:** `esp_lcd` 패널 드라이버, LVGL 구조, DMA 플러시 버퍼가 왜 내부 SRAM을
써야 하는지 (Phase 1의 정책이 여기서 실제로 쓰인다)

**산출물:** 동작하는 대시보드

---

## Phase 4 — 부하 걸기 + 데모 (1주)

압박이 없으면 그래프가 평평하다. 움직이게 만든다.

- [ ] 합성 부하 — 불규칙한 크기로 할당/해제 반복해 단편화 유발
- [ ] 트리거 (버튼 또는 시리얼 명령)로 부하 on/off
- [ ] Wi-Fi 연결 + HTTPS 반복 요청 (`esp_http_client`)
      — TLS 핸드셰이크가 같은 힙을 쓰므로 단편화가 자연 발생한다
- [ ] 데모 영상 촬영 (단편화 그래프가 치솟는 장면)
- [ ] 프레임버퍼 덤프 유틸 — 포폴 이미지용 (LCD 직촬은 모아레로 품질이 나쁨)

**배우는 것:** 단편화가 실제로 누적되는 과정, TLS 스택의 메모리 사용 패턴,
서드파티 라이브러리가 만드는 할당은 내 통제 밖이라는 사실

**산출물:** 데모 영상, 스크린샷

## 나중에 여유가 생기면

당장은 범위 밖. 더 파고들고 싶을 때의 확장 방향.

- **정책을 교체 가능하게** 만들어 고정 임계값 방식과 단편화율 기반 적응형 방식을
  같은 부하에서 비교 → "왜 이 임계값인가"에 측정으로 답할 수 있게 된다
- **mbedTLS 할당자 후킹** (`mbedtls_platform_set_calloc_free`) — 단편화의 주원인을
  정책 통제 범위로 편입
- **계측 오버헤드 정량화** — 대시보드 on/off로 같은 부하를 돌려 비교
- **메모리 출처별 분리 계상** — 앱 / 서드파티 / 계측 자신
