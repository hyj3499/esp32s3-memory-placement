# freertos-multiheap-manager

**ESP32-S3 메모리 배치 정책을 측정으로 결정하기**
— "TLS가 먹는다"고 믿었던 내부 SRAM 78KB의 정체를 추적한 기록

> 진행 중인 개인 학습 프로젝트입니다. 아래 숫자는 전부 실기(Guition JC4827W543,
> ESP32-S3 + 8MB Octal PSRAM) 실측이며, 재현 조건과 함정까지 `docs/STUDY.md`에
> 남겨두었습니다.

---

## 문제

ESP32-S3에는 성격이 다른 메모리 두 개가 있다.

| | 내부 SRAM | 외부 PSRAM |
|---|---|---|
| 용량 | 약 390KB (Wi-Fi 구동 시 260KB대) | 8MB |
| 속도 | 코어 클럭 | 40MHz Octal, 캐시 경유 |
| DMA | 가능 | 제약 있음 |

**대체 자원이 아니라 용도가 다른 자원**이다. 어떤 버퍼를 어디에 두는가가 성능과
안정성을 가른다. 그런데 IDF는 이 배치를 Kconfig 심볼 수십 개에 흩어 놓았고,
**각 심볼이 실제로 무엇을 얼마나 옮기는지는 문서에 없다.**

이 프로젝트는 그걸 하나씩 재서 답했다.

---

## 접근 — 왜 "측정"이 본론인가

처음에는 할당 래퍼를 만들 계획이었다. 크기·DMA 필요 여부·수명을 입력받아 리전을
결정하는 정책 엔진. **측정해 보니 그 래퍼가 옮길 것이 거의 없었다.**

효과가 있었던 레버는 전부 **설정 결정**이었고, 그 결정은 **측정 없이는 내릴 수
없는** 것이었다. 실제로 이름만 보고 켰다가 손해를 본 스위치가 있고, 산술로 예측한
결과가 통째로 틀린 경우도 있다(아래 "뒤집힌 통념" 참고).

그래서 이 저장소의 산출물은 할당기가 아니라 **계측 하네스 + 배치 정책 결정표**다.

## 결과

HTTPS 반복 요청(매 요청 새 TLS 핸드셰이크) 부하 아래에서 측정.

| | 기본 설정 | mbedTLS PSRAM 적용 후 | 차분 |
|---|---|---|---|
| 핸드셰이크 피크 (`min_free`) | 78,347 | **47,039** | −31,308 |
| 부하 중 최대 연속 블록 | 147,456 | **176,128** | **+28,672** |
| 첫 요청의 단편화 손실 | 32,768 | **4,096** | 1/8 |

`largest_free_block`이 핵심 지표다. 총 여유가 260KB여도 조각나 있으면 큰 버퍼
할당은 실패한다. 이 보드의 LCD 프레임버퍼(480×272×2 = 261,120)를 기준자로 쓰면
부족분이 113,664 → **84,992**로 줄었다.

### 그리고 남은 47,039의 정체

heap tracing으로 콜스택 6단까지 추적해 270건을 전수 분류했다.

| 주체 | 바이트 | 건수 | 비중 |
|---|---|---|---|
| **Wi-Fi 드라이버 `esf_buf`** | 33,292 | 39 | **63.9%** |
| **lwIP `pbuf`/`mem`** | 9,272 | 85 | **17.8%** |
| 하드웨어 AES DMA 바운스 | 4,256 | 63 | 8.2% |
| 그 외 (esp-tls / http_client / FreeRTOS) | 5,286 | 83 | 10.1% |

**"TLS 피크"라 불러온 것의 82%가 Wi-Fi와 lwIP였다.** 순수 TLS 몫으로 남은 것은
`esp_tls_init`의 1,764바이트가 거의 전부다. 그리고 이 82%는 `wifi_malloc`과
`mem_clib_malloc`을 지나가므로 **mbedTLS 훅으로는 건드릴 수 없다** — 래퍼를 먼저
만들었다면 무엇을 옮기는지 설명하지 못했을 물건이 나왔을 것이다.

## 실측으로 뒤집힌 통념

각각 독립적으로 재현했고 근거 소스 위치를 함께 남겼다.

**① `SPIRAM_TRY_ALLOCATE_WIFI_LWIP`은 켜면 손해다 (내부 −17,868).**
이름은 "Wi-Fi/lwIP를 PSRAM으로"지만, 배치 정책과 용량 정책이 한 심볼에 묶여 있어
(`esp_wifi/Kconfig:82`의 `depends on`) TX 버퍼가 dynamic→static으로 강제 전환된다.
같은 TX 구성끼리 비교하면 실제 이동량은 13%뿐이다.

**② mbedTLS는 `malloc`을 쓰지 않는다.**
`CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC`(기본값)이 `esp_mem.c:17`에서
`MALLOC_CAP_INTERNAL`을 **명시**한다. `SPIRAM_MALLOC_ALWAYSINTERNAL` 임계값도,
PSRAM 관련 다른 스위치도 이 경로에는 영향이 없다. **컴포넌트가 자기 할당자 정책을
따로 갖는다.**

**③ Kconfig 한 줄이 바이너리 크기를 안 바꿀 수 있다.**
`INTERNAL`→`EXTERNAL` 전환 후에도 `.bin` 크기가 `0xed090`으로 동일했다. 반영 실패를
의심해 오브젝트를 디스어셈블했더니 `movi a12, 0x404`(SPIRAM|8BIT) — 바뀐 것은
즉시값 하나뿐이라 **코드 크기 델타가 구조적으로 0**이었다.

**④ PSRAM으로 옮기면 하드웨어 AES가 바운스 버퍼를 새로 잡는다.**
`esp_aes_dma_core.c:259`는 입출력 중 하나라도 외부 RAM이면 DMA용 임시 버퍼를
할당한다. mbedTLS를 PSRAM으로 보낸 대가로 내부에 4,256바이트가 새로 생겼고,
청크마다 `memcpy`가 붙는다. **이득만 있는 배치 변경은 없다.**

## 계측 하네스 — 관측자 효과를 피하는 설계

계측이 관측 대상을 오염시키면 측정이 의미를 잃는다. 두 방향 모두에서 막았다.

**메모리 쪽.** 부하 생성기와 모니터 태스크의 스택·TCB·이벤트그룹·싱크 버퍼를 전부
정적으로 잡았다. `xTaskCreate`를 쓰면 스택이 힙에서 나온다. 대가는 힙 풀 14,288
축소이고, **"매번 달라지는 작은 값"보다 "한 번 확인하면 끝인 큰 값"이 낫다**는
판단이다. heap tracing 레코드 버퍼(76바이트 × 1024)도 `EXT_RAM_BSS_ATTR`로 PSRAM에
내보냈다.

**시간 쪽.** IDF의 `heap_trace_dump_caps()`는 덤프 전체를 하나의 critical section
안에서 돌린다. 레코드 264개를 115200 baud로 뱉으면 인터럽트를 2.3초 끈 채 있게 되어
인터럽트 워치독이 코어를 죽인다. 실제로 죽었고, `heap_trace_get()`으로 직접 순회해
critical section을 레코드 하나 길이로 줄였다. (`docs/TROUBLESHOOTING.md #3`)

## 측정 방법론

- **조건 고정 A/B.** 변수 하나만 바꾸고 나머지(요청 간격·스냅샷 주기·AP·코드)를
  전부 묶는다. 힙 풀 크기·부팅 직후 free·Wi-Fi 비용이 바이트 단위로 일치하는 것을
  먼저 확인한 뒤에야 차분을 믿는다.
- **절대값이 아니라 차분.** `largest_free_block`은 TLSF 크기 클래스 내림값(오차
  최대 3.1%)이고 `frag%` 공식은 여러 힙 합산 때문에 값을 부풀린다. 오차는 양쪽
  빌드에 같은 방향으로 실리므로 차분에서 상쇄된다.
- **피크는 `min_free`로만 잡힌다.** 5초 주기 샘플링은 45회 내내 78KB 피크 중 38KB를
  놓쳤다. 주기를 줄이는 것으로는 해결되지 않는다 — 계측 자체가 부하가 된다.
- **재현성 확인.** 독립 실행 두 번에서 내부 할당 합계가 52,098 / 52,106(8바이트 차),
  `largest`는 완전 동일.

함정의 상세는 `docs/STUDY.md §7`에 있다.

## 구성

```
main/
  heap_manager.c     app_main. 부팅 baseline → Wi-Fi → 모니터 → 부하
  wifi_conn.c/h      STA 연결 + 초기화 단계별 계측 (A~E 지점)
  mem_snapshot.c/h   리전 4종 스냅샷 / 한 줄 요약
  mem_monitor.c/h    주기 출력 (시간축)
  http_load.c/h      HTTPS 반복 요청. 요청 N회마다 스냅샷 (요청축)
  heap_probe.c/h     heap tracing 래퍼. 첫 핸드셰이크만 추적 + 크기 분포
```

외부 컴포넌트 의존 없음. 설정은 `menuconfig`의 `Multi-heap Manager` 메뉴,
변경 근거는 `sdkconfig.defaults`에 주석으로 남긴다.
